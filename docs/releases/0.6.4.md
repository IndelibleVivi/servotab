# Servotab 0.6.4 candidate — evidence-scoped debugging

Status: source candidate, not a published release or installed update. Publication, directory submission, activation, deployment and live model evaluation remain separate actions. The last recorded published version is 0.6.3.

## Changes

This candidate sharpens existing `debug` and `verify` decisions without adding a skill, runtime service, dependency, required report or evaluation runner. The existing router already covers unknown causes, conflicting evidence and repeated failure; it stays unchanged.

`debug` separates the mechanism experiment from final acceptance. A surrogate must preserve the conditions relevant to the tested cause. Trial results can be supportive, contradictory or inconclusive; an unverified intervention or failure to restore the whole experience does not erase a contributing defect. Direct boundary violations and loss of discriminating evidence prompt an earlier diagnostic reset. Counts remain a backstop, and a reset does not automatically require an architecture search. Permanent repairs follow component and lifecycle ownership.

`verify` checks probe entry, path and conditions, pairs disappearing errors with successful outcomes, separates mechanism repair from complete recovery, and prefers structured or stable normalized before-images for state-preservation claims.

## Diagnostic cases

Three cases extend the existing source pack from twenty to twenty-three:

- `cross-boundary-diagnosis`: a local executable admission model with healthy bypass probes, a confounded earlier trial and an independent residual delay. Acceptance requires actual comparable pre/post experiments and successful delivery, not a proposed plan or an edited counter.
- `host-specific-diagnosis`: a desktop probe lacks a material native-host condition and cannot exclude that cause.
- `diagnosis-progress`: successive experiments make real causal progress despite incomplete overall recovery; a numeric failure count must not trigger a pointless restart.

The existing Field Lab schema, baseline/expected overlays and semantic-review boundary are reused. New deterministic fixture regressions check red/green delivery, residual symptoms, non-exempt paths and incorrect repairs. Expected reports are reference controls, never fabricated attempt receipts. Semantic requirements must be judged from real attempt evidence.

## Validation and release boundary

Run the repository's existing source/package gate and `python3 -m unittest discover -s scripts -p 'test_*.py' -q`. The new focused controls can be run with `python3 -m unittest discover -s scripts -p 'test_diagnostic_fixtures.py' -v`. Exact-source CI and review records determine candidate readiness; the version string does not.

No paid model calls, live router changes, host installation, directory upload, deployment or publication are part of this candidate. Fixture success establishes fixture mechanics, not improved agent behavior. A future live attempt needs its own explicit invocation budget and review under the existing evaluation contract.
