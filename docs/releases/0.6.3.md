# Servotab 0.6.3 candidate

0.6.3 expands `worktree` from isolation setup into workspace lifecycle guidance: find the right task, reuse or restore its workspace, create isolation when it solves a real conflict, and park or clean up only within the authorized scope.

This is source-candidate documentation. It does not announce a tag, GitHub Release, installation, activation, website deployment, or directory update. The published install target remains 0.6.2 until separate publication evidence changes it.

## Changed behavior

- Calling `$worktree` no longer implies creation. Inspection and organization requests produce concrete dispositions without authorizing deletion. The ordinary-language router recognizes recovery, parking, and cleanup as well as isolation.
- Creation first checks existing task workspaces and reconciles ambiguous earlier results. Dirty state, duration, risk, or worker count alone do not demand a new checkout. Verify required starting content: ordinary Git creation at a revision does not transfer dirty prerequisites, while host tools have their own contracts.
- Parking can release an inactive, unmerged checkout with a durable named ref and a restoration route. It does not auto-commit, stash, archive, upload, merge, or delete the branch.
- Cleanup checks ignored data, tracked edits hidden by `assume-unchanged` or `skip-worktree`, detached tips, current integration targets, active ownership, locks, in-progress Git operations, submodules, and unavailable storage where relevant. Directory removal, local/remote branch deletion, data disposal, and registration pruning remain separate actions.
- Flagged tracked files that are present need a content comparison without changing the real index or its flags, or the candidate stays unresolved. Ordinary status and non-force removal do not prove that these local edits are preserved; a retained branch restores committed content only.
- Exact existing authorization is reusable for a concrete batch. Recheck each item before removal, leave changed or uncertain items pending, execute independent approved items, and verify preserved refs afterward.
- `finish` shares the removal contract. `delegate` now explains that different branch names in one checkout do not separate working files or indexes, and that worktrees still share refs and may share runtime resources.

The one-router/twelve-leaf topology, 70-file package, skills-only product boundary, and licenses remain unchanged. No runtime cleanup executor, new dependency, global registry, or unattended deletion service is added.

## Evidence and limits

The source pack contains twenty cases. Three new synthetic decision rehearsals cover reuse after ambiguous creation, inspection-only organization with mixed risks, and already authorized parking with one changed candidate. Structural checks verify output existence and write scope; declared semantic review requirements judge the decisions. The explicit `worktree-organize` case requires actual leaf delivery/read evidence in semantic review; it does not require a redundant router-reference read. Deliberately unsafe or obstructive outputs remain adversarial controls because correct labels cannot prove sound reasoning.

`scripts/test_worktree_git.py` checks the underlying Git mechanisms in disposable local repositories: ignored-data deletion, non-mutating hidden-tracked-content inspection and loss on removal under both index flags, unmerged named-ref preservation/restoration, detached tips without named anchors, squash/ancestry differences, dirty prerequisites, locks, and missing/moved registrations. These tests do not execute a target model or prove host-managed cleanup behavior. The rehearsal cases do not execute real cleanup either; a future live operational case needs its own fixture, saved plan, and explicit invocation budget.

The canonical package gate, fixture controls, and site checks validate source consistency and their stated mechanisms. No live 0.6.3 model-effectiveness result is claimed. Actual candidate verification and publication state belong in [current state](../current-state.md).

## Operational basis

Git distinguishes per-worktree files/indexes from shared refs, documents lock/repair behavior, and defines pruning as removal of stale administrative records. Use the supported host lifecycle where it owns a workspace. See the official [Git worktree documentation](https://git-scm.com/docs/git-worktree) and [branch deletion contract](https://git-scm.com/docs/git-branch). The official [index flag documentation](https://git-scm.com/docs/git-update-index) and [file-tag inventory](https://git-scm.com/docs/git-ls-files) explain the hidden-state check. Git's acceptance of a removal is not evidence that all local data was disposable or that a branch was integrated.

Update the source package through the existing marketplace route when deliberately testing this candidate; no migration or legacy retirement is required. An installed 0.6.2 package keeps the earlier worktree guidance until updated and rediscovered by its host.
