## 1. 要解决的问题

用户经常带着明确的目标、充分讨论过的方向，直接委托工程机完成工作。方向清楚以后，仍有一些决定必须结合现场做出：先连接哪条路径，哪个假设值得提前验证，哪里需要更多制作投入，哪些实现细节可以留到接近执行时决定，以及换会话后如何接续。

Plan 的职责是形成并维护这些执行策略。它应当在普通工程请求中适时介入，让已经授权的工作继续；用户无需记得开启某个 harness 的 `/plan` 模式，也无需反复追加“请按任务规模规划”。

成功体验包括：

- 清楚的局部工作直接完成，必要检查不会因为没有计划文件而被省略。
- 多环节工作有实际依据的先后与投入差异，早期成果足以判断关键机制或整体体验。
- Chat brief、规格与现场实现能够顺畅衔接，已定目标不会被重新访谈，旧方案也不会未经核对直接变成施工事实。
- 重要发现会改变受影响的后续安排，完整交付范围持续保留。
- 跨阶段、跨会话或跨执行者工作，能够从仓库内的当前记录恢复，减少用户重复交接。

Plan 的价值用行动与结果判断。生成较长的 Markdown、宣布使用技能、调用原生计划工具，都不能单独证明上述能力。

## 2. 为什么在 St 内完成

本轮沿用现有 `plan` leaf，不新建仓库、独立插件、额外 router 或计划服务。通用方法在 St 的真实工程任务中接受检验，具有独立价值的部分以后可以迁移；当前不提前建设跨 harness 适配平台。

审阅基线已经具备以下基础：

| 当前基础 | 本轮保留与发展方向 |
|---|---|
| 一个隐式可选的 `servotab` router，十二个显式 leaf | 保留拓扑，由 router 自动读取所需方法；`plan` 显式入口继续可用。 |
| `plan` 已要求完整范围、真实依赖、首条可观察执行路径、验证与交接 | 保留已有能力，补足触发、投入分配、条件化策略、持续修订与恢复行为。 |
| `plan` 发现描述偏向“为已明确工作创建实施计划” | 更新描述与提示入口，使普通实施请求和执行中重排也能获得方法。 |
| `execute` 已接收明确请求或已有计划，支持连接后的切片与证据反馈 | 消除“需求明确即可跳过全部策略判断”的歧义，执行中继续使用同一计划。 |
| `spec-chain` 已维护完整规格覆盖及阶段边界 | 复用现有覆盖记录，不创建第二套需求台账。 |
| canonical 方法由构建器投影为 leaf 与 router reference | 继续由同一方法正文生成两种交付面，避免维护两份 Plan。 |

以上属于源码与合同观察，尚不能据此断言当前模型日常使用一定漏掉规划，或新版本一定提高效率。新增行为需要与现有基线对照。[^st-contract][^st-plan][^st-catalog][^st-builder][^st-execute][^st-spec-chain]

## 3. 范围与交付边界

### 3.1 本轮包含

升级自动介入判断、执行策略方法、持久计划的完整生命周期，以及与执行、规格覆盖、领域方法、委派和验收的必要衔接。交付应包含 canonical 源码、生成产物、相应文档、行为场景和有边界的实跑证据。

“策略形成”和“持久记录”是同一项能力的不同部分。只添加 Markdown 模板，或只增加“复杂任务要规划”一句提示，都未完成本规格。

### 3.2 本轮不引入

不新增计划数据库、后台 daemon、任务调度器、通用 DAG 引擎、跨会话锁服务、全局状态索引或自动读取私人 session 历史的机制。没有固定的每任务访谈、spike、worktree、子代理或多重审阅流程，也不批量改写使用者的全局 `AGENTS.md`。

Soundings 与 Frontend Craft（FC）是可协作的方法来源。本规格不要求安装它们，不顺带重构它们的仓库，也不把它们的专业判断复制成 St 内的平行系统。

保持现有权限与验证合同。方法自动介入不扩大当前委托：仅规划、仅审阅、禁止写入、禁止外部调用等边界仍有效。

## 4. 方法归属与自动介入

### REQ-01：普通请求能够触发策略判断

router 应当在进入有后果的行动前，识别是否存在尚未解决、且足以影响后续安排的执行选择。已经接受工作目标，不代表顺序、投入与验证路径已经解决。

以下情况支持加载 Plan：

- 多个实现环节依赖一个尚未核实的机制、接口或解释；错误会在后续工作中扩散。
- 不同顺序会明显改变返工成本、集成可信度，或用户能否尽早判断整体质量。
- 工作需要有意义的阶段、交接、迁移或恢复安排。
- 已有计划与新发现、当前实现或用户修正发生实质冲突。
- 用户明确要求规划。

不以文件数量、工具调用次数、提示词长度或“复杂”标签作为充分触发依据。大量同构修改可直接执行；很小的状态或权限修改仍可能需要策略和相应验证。

明确局部工作不需要另写计划。成熟的多步路径已经有可用方案时，核对后继续即可。正在发生因果调查时，`debug` 保持调查职责；只有整体推进或恢复安排需要调整时，才增加 Plan 的贡献。

### REQ-02：继承已完成的思考与当前权限

进入 Plan 时恢复当前目标、接受标准、已定选择、有效计划、现场事实及重要未知。区分用户已选择的结果、工程机提出的机制、观察支持的事实和仍可现场决定的实现细节。

由仓库和工具可查明的事实，应自行核实。不要让用户重新描述已存在于当前材料中的目标，也不要把措辞完整的 Chat brief 当作已验证的现场设计。

遇到未定问题时，只阻塞实际依赖它的工作。工程机可以在现有授权下作出普通可逆实现选择；确实改变产品意义、重要取舍或外部后果的未授权决定，交还相应决定者。结束一次方法介入不新增“是否继续”的审批环节。

### 职责边界

| 方法或参与者 | 当前职责 |
|---|---|
| St router | 选择必要方法与责任归属；不重复展开整个计划正文。 |
| `design` | 解决实质产品、交互和架构选择。 |
| `plan` | 组织推进顺序、投入、证据时机、阶段与交接，并维护策略。 |
| `execute` | 实施与观察，反馈导致策略变化的事实，更新同一工作记录。 |
| `spec-chain` | 保持已接受规格、完整覆盖及适用的范围／顺序变更。 |
| `debug` / `verify` | 分别承担因果定位与完成证据判断。 |
| `delegate` | 决定实际委派、责任与返回合同；Plan 提供依赖与协作需求。 |
| 领域方法 | 提供专业质量、代表性、制作与验收要求。 |
| `finish` | 按当前授权关闭工作与记录，处理允许的 Git 等动作。 |

Plan 不成为覆盖这些方法的新总控流程。已有 lane、计划与责任人在方法切换时继续有效。

## 5. 执行策略应当作出哪些决定

### REQ-03：依据结果安排投入、顺序和细节深度

对需要策略的工作，应形成足以指导近期执行的判断：

**结果和质量重心。** 明确什么结果使这项工作值得做；哪一部分的额外制作、验证或理解最可能改善成果。完整验收范围保持不变，各部分可以获得不同投入。

**真实依赖。** 同时考虑实现依赖和判断依赖。编译顺序只覆盖前者；一个 UI 可能必须带入真实内容、素材和完整操作，才看得出布局是否成立。

**先固定什么。** 已接受的产品决定持续有效。高返工代价的机制需要相应依据；普通内部细节可以由接近实现的执行者决定。不要为了“decision complete”穷尽所有未来分支。

**近期怎样推进。** 写清下一段有意义的结果、相关实现区域和检查路径。检查代码后再命名真实文件；无法确定的触点可以描述为已定位的区域，不编造精确路径。

**什么会改变路线。** 对能够推翻后续工作的关键假设，记录支持条件、可区分的观察，以及被影响的工作。无需列举所有假设。

**何时可以直接继续。** 有成熟证据、风险局部且完成路径清楚时，直接实现。方法需要支持这种选择。

这些是判断义务，不能变成每项任务必须填完的六栏表格。规划深度、输出长度、持久化和是否等待用户应分别决定。

资源判断考虑实际可用工具、领域制作成本、现有责任人以及明确的调用预算。未知配额和模型能力不得编造成数字；工具暂缺时说明受影响的工作，继续可完成部分，不能静默缩小整体结果。

### REQ-04：足够早地产生有判断力的成果

跨组件任务应尽早通过真实入口、关键状态或边界取得可观察结果。若关键路线已知，直接连通并观察；只有会改变路线的问题才值得单独探查。

观察材料的完整度必须匹配所作判断。需要实际 GUI 的体验，单独 CLI 成功不能证明；需要内容、图像和操作反馈共同成立的界面，空白占位骨架不足以验证。高质量素材和制作工作可以成为早期任务的必要部分。

第一次有用观察不能自动变成最终交付。主计划继续覆盖剩余功能、状态、集成和验收。若用户明确选择原型范围，则按该范围执行，不擅自扩成完整产品。

对有前置基础设施或迁移约束的任务，先完成必要前提。使用 surrogate 或 fixture 时注明它实际覆盖的边界，避免为了展示“端到端”跳过真实依赖或先做不适用的薄片。

### REQ-05：按证据修订，能结束规划与探索

执行中的重要观察、用户修正、能力变化或计划失效，应触发局部重新规划。更新受影响的决定、阶段与验证，保留独立成立的目标和工作。

路径改名、已存在的可复用函数等局部事实，可以直接修正并继续。关键架构前提被推翻时，回到相应设计或调查；不能继续扩展旧方案，也不能无依据重开整项需求讨论。

完整范围中的近期部分应足够可执行，依赖后续观察的细节可以保持条件化。到达有意义的阶段边界后细化下一段，避免在开头写满大量会失效的细节。

当近期路径、相应权限与验收已经足够清楚，停止本次规划介入。实施继续到当前请求的结束点。对没有增加区分性证据的重复尝试，应改变调查或制作方式，不能把无限“再探查一次”包装成策略。

## 6. 持久计划的生命周期

### REQ-06：在需要连续性时主动保存

出现以下连续性需求时，应建立或更新持久记录，无需用户额外要求：

- 工作将跨会话或由另一位执行者接续。
- 存在有独立结果与依赖关系的阶段，关键决定仅靠 diff 难以恢复。
- 迁移、部署准备、分批交付或中断恢复需要记住准确边界。
- 多条工作 lane 需要共享目标、依赖和完成状态。
- 用户明确请求计划文档。

不要把一次普通修复的“定位、修改、测试”三个步骤自动解释成需要三份阶段文件。同一会话可以可靠完成的清楚工作，允许只有行内策略。

**先复用。** 检查本任务已选记录和仓库约定。有有效计划时继续维护；缺一节就补一节，不能为了套用新模板重写整个计划或复制一份。

**再选择位置。** 没有既有约定时，共享工程计划默认建议 `docs/plans/<task-slug>.md`。名字应稳定描述任务，日期可作为仓库命名习惯。规格可放在 `docs/specs/`。这些是回退约定，不是每个仓库都需建立的目录。

**选择可见范围。** 可共享的工程目标、决策原因和验证依据适合留在仓库；私人对话、账号细节、敏感本机环境与原始 session 记录留在约定的私有位置。公共计划应足以承担公共范围的实施，不以不可见私人材料作为隐藏前提。

写入工作区与提交 Git 是独立动作。适用的文档写入可以包含在当前工程委托中；提交与发布仍沿用现有权限。只读任务不写目标仓库；需要交付计划文件时，使用当前允许的输出位置并注明未落仓库。

### REQ-07：一项连贯工作保留一个当前计划入口

默认一份主计划承载阶段。阶段具有独立责任人、明显不同的执行上下文，或证据量使单文件难以使用时，可拆分阶段文件。主计划保留完整结果、阶段依赖、当前入口及剩余范围。

不得用全仓库唯一的可变 `active_plan.md` 隐式绑定所有并发任务。本任务通过明确路径或既有任务记录识别计划；并发 lane 继承各自选定的入口，不按“最近修改的文件”猜测。

计划需要表达以下信息，具体标题与排版可沿用项目习惯：

| 信息 | 语义要求 |
|---|---|
| 任务身份与当前状态 | 哪项工作、哪个目标，是否仍在继续；适用的源码或环境基线。 |
| 已定目标与验收 | 引用规范来源及必要条件；无正式 spec 也能工作。 |
| 当前策略与重要假设 | 为什么这样推进，什么观察会改变受影响部分。 |
| 阶段与完整范围 | 各阶段形成什么结果、真实依赖和未完成部分。 |
| 验证与观察 | 检查对象、结果、适用基线及可用证据位置。 |
| 当前接续 | 下一段应形成的结果；真正的阻塞及可继续部分。 |
| 重要变化 | 改变路线的原因与影响；无须记录全部工具调用。 |
| 关闭与后继 | 最终结果、仍未验证部分，以及替代计划或正式文档入口。 |

较大的已批准规格继续使用 `spec-chain` 的完整覆盖记录。轻量计划无需另造全局需求编号。已存在的 issue、阶段表和 native task list 能承担部分信息时，使用链接或投影，不多建一份同义进度源。

状态应区分待做、进行中、已实现但未验证、已有适用验证、阻塞、取消或被替代等语义。它们不构成需要新增解析器的固定枚举。仓库可采用已有词汇；不能用一个 `done` 同时宣称源码、安装、部署和用户接受。

### REQ-08：读取、更新、恢复与关闭必须共同成立

**更新时机。** 重要结果落地、假设被推翻、阶段转换、决定影响后续工作，以及有意识的交接或结束时更新记录。不要按固定工具次数或计时器强制更新。无法预知的进程中断可能留下旧记录，因此恢复过程必须容忍不一致。

**当前有效内容在前。** 更新路线、阶段和下一步，简短保留变化原因。避免堆叠互相冲突的追加日志，或不断新建 `final-v2-revised` 文件。历史细节可链接到相关 commit、PR、实验记录；本轮不新建日志服务。

**恢复流程。**

1. 根据明确委托、仓库约定和已有任务入口，定位当前任务的计划。若有多个可能对象，先用任务与 workspace 证据消歧；无法安全消歧时只阻塞依赖选择的写入。
2. 读取当前目标、有效策略、相关阶段与接续项。读取会影响下一步的规格、决策和证据，不要求无差别加载全部历史。
3. 核对相关 Git 状态、实现、测试与必要环境。计划是定位事实的入口，不能以旧勾选代替当前事实。
4. 检查计划落后于代码、代码落后于计划、测试过期和部分执行等情况。修正状态，保留未知；不自动重放可能已产生外部后果的动作。
5. 在现有授权内继续下一段工作；不重新访谈已定目标。

计划缺失但工作仍可从有效规格与当前实现恢复时，重建必要部分，并标明恢复出的事实与推定。原计划过长时可以整理当前视图，不能顺手丢掉未完成范围和关键变更原因。

**写入责任。** 一项协作任务指定一个当前主计划维护者，通常由现有协调者承担。worker 在其明确分配的文件内记录或返回结果；未经分配不共同改写主计划。写入前检查当前内容与相关 diff，避免覆盖他人的新变化。本轮依赖现有责任与 workspace 约定，不新增锁基础设施。

**关闭。** 完成时记录实际结果、证据和遗留状态。替代时记录后继入口；暂停与取消保留理由，不伪装成完成。长期成立的架构或使用结论进入已有正式文档并链接回计划，历史计划不成为永久的操作手册。默认不批量删除历史计划。

## 7. 与 Soundings、FC 及 native harness 的协作

### REQ-09：保持同一项工作的上下文与质量标准

Soundings 已将目标、已定选择、提案、证据、未知和行动权限区分，并要求跨方法延续同一任务；仅在需要连续性时持久化。St 应承接这个结构，避免另建 Soundings 专属计划。[^soundings-context]

**Search / Study。** 提供会改变实施判断的事实、综合结果、条件和可复读证据。St 将影响写入同一策略；来源与解释可链接到已有研究记录。

**Shape。** 当不同理解会产生实质不同的产品、架构承诺或验收时参与。已经授权且不依赖该选择的工作继续。修正一个理解时，Plan 更新受影响阶段，不遗失其他目标。

**Explore。** 发展有实际效果的候选或代表性成果，提供可以判断的材料。Plan 为制作及观察安排工作，不要求每次探索都先长成正式规格。

**FC。** 提供整体构成、素材、操作生命周期、代表性内容、renderer 与体验验收要求。若判断必须依赖足够完整的表面或交互，Plan 将其作为真实依赖，不能统一压成低保真骨架。构建通过不覆盖视觉与体验接受。

**接续信息。** 方法或执行者切换时，携带目标、已定选择、当前路径、关键条件、证据、适用权限和未完成部分。使用现有记录与责任 lane，无需新 brief、固定 pipeline 或统一 JSON 协议。

### REQ-10：安静执行，独立控制输出与工具

用户侧只需看到会影响理解、取舍或进度的内容：选定路线的重要原因、已经形成的结果，以及真正改变后续工作的发现。没有必要宣布技能名、展示全部内部比较过程或每阶段重新征求继续许可。

已授权实施时，规划后继续执行；明确只要 plan/spec 时，停在相应交付。自动介入不自动切换 harness 的 Plan Mode。

可使用 host 原生计划／任务工具显示当前阶段，但它应反映同一策略。跨会话需要持久性时，原生清单不能替代仓库记录；仓库计划存在时也无须逐段复制到 UI。没有该工具的 host 仍可按方法工作，不新增 shim。

本轮默认实现维持 St 的当前分发面。方法文字减少对特定斜杠命令的依赖，不据此宣称已在其他 harness 安装或运行通过。hooks 的自动注入可以留作后续有证据的扩展，当前先通过方法约定在真实接续与决策点重新读取。

## 9. 行为验收

### REQ-12：验证适时使用、实际推进与可靠恢复

### 9.1 分层检查

**源码与打包。** 检查 canonical／generated 同步、metadata、引用、包清单与现有测试。固定字符串出现只能证明文案或结构，不能证明策略生效。

**行为场景。** 在已知任务与 fixture 中观察方法选择、行动顺序、检查、文件写入和最终覆盖。不得只按“读过 Plan”或“输出包含若干标题”判分。

**真实使用。** 至少覆盖 St 自身升级这一项纵向 dogfood，以及一个独立于本规格内容的工程任务。可以从领域代表性场景中选择第二项，不要求为评估新建无关产品。保留成功与失败观察及适用范围。

案例是应覆盖的行为类别，可以合并到少量高质量 fixture；不要求一行矩阵对应一个新评估系统。准备能推翻漂亮但错误输出的隐藏变体，并包含方法应当保持安静的负控。

### 9.3 对照与观察方式

比较旧 St 与候选版本时，固定输入、起始源码、模型设置、工具权限及可用时间／调用预算。对自动触发场景，输入不包含 `plan` 或“先规划”；显式仅规划作为独立控制组。

检查实际动作及产物：有意义的证据何时出现，是否出现围绕失效假设的重复工作，范围是否完整，用户被要求补交哪些决定，记录能否支持接续。token、调用数、耗时和文本长度可以记录为成本背景，不单独决定优劣；高质量完整交付允许比低质量薄片花费更多。

核心正例与负控需要复跑，保留所有结果及环境差异。实跑规模由单独、有明确预算的试验计划确定，不把本规格当成无限模型调用授权。

接续实验应给新会话任务入口和仓库，不附原始聊天；同时测试准确记录、过时记录及部分缺失记录。当前 fixture、测试和执行轨迹是独立证据，计划的自我陈述不参与自证。

方法选择与结果归因分开：模型即使没有显式调用 leaf，也可能已有正确行为；读取过方法也可能照旧执行。需要指出改善具体发生在哪项判断或动作，避免把基线本来会做的事全部归功于新版本。

## 10. 完成标准与实验推进

本规格的完整交付同时要求：

1. REQ-01 至 REQ-12 已映射到实现及适用验证。方法正文、发现描述、router、execute、记录生命周期与领域衔接形成同一条可用路径。
2. 保留当前直接工作、完整规格覆盖、风险匹配验证和权限边界；没有平行 Plan 实现或多余运行时系统。
3. canonical 与生成产物通过当前仓库要求的源／包检查，相关文档一致。
4. 行为场景及纵向 dogfood 提供可检查证据。观察到的未解决失败保留状态，不能用打包绿灯覆盖。
5. 发布说明区分源码候选、安装／发现、适用行为证据、发布与其他环境验证。未运行的验证明确列出。

可以分多次提交、PR 和会话交付。源与包完成但行为未测时，记录为候选并继续验证；不能报告“已经证明能自动规划”。一次行为成功也不能推广成所有模型和 harness 的效果保证。

### 当前实施不需要等待的新结论

本轮已经选择在 St 内升级现有方法，保留一个隐式 router，持久计划使用仓库约定并具备完整生命周期。无需先完成所有跨 harness 适配、方法理论或自动注入机制，才能开始实施。

仍需由使用证据检验的命题包括：策略触发是否过宽或过窄；持久记录是否降低重复交接；领域条件能否改变实际顺序；较短运行时说明是否仍能保留必要判断。试验可以修改具体措辞和实现技巧，涉及本规格的产品范围或接受标准变化时留下明确 delta。

后续只有出现真实使用压力，才考虑独立模板、host hook、计划定位 helper 或跨 harness 适配。连续性首先通过读写习惯、有效记录和接续验收建立。
